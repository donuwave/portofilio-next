# Деплой на VPS

## Шпаргалка: как выкатить изменения

Всё делается у себя на компьютере, в папке проекта, при запущенном Docker Desktop:

```bash
./scripts/deploy.sh
```

Скрипт сам собирает образ, отправляет на сервер только изменившиеся слои, перезапускает сайт и дожидается ответа. Повторный деплой без изменений занимает секунд 10, с изменениями в коде обычно 1–3 минуты (основное время — сборка под x86 через эмуляцию на Mac). Первый деплой после чистой установки дольше, потому что отправляется всё.

- **Откатиться**, если новая версия сломалась: `./scripts/deploy.sh --rollback`.
- **Только проверить сборку**, ничего не отправляя: `./scripts/deploy.sh --build-only`.
- **Перед деплоем** лучше сделать `git commit`: образ собирается из текущих файлов (в имени будет `-dirty`, если есть незакоммиченное), и коммит нужен, чтобы знать, что именно сейчас на сервере.
- **Что делать, если деплой упал:** прочитай последние строки вывода, сайт при этом продолжает работать на предыдущей версии: контейнеры перезапускаются только после успешной отправки образа.
- Смотреть, что происходит на сервере: `ssh -i ~/.ssh/id_ed25519_portfolio deploy@194.87.190.164`, дальше `cd /opt/portfolio && docker compose --env-file .env.prod -f docker-compose.prod.yml logs -f app`.

---

Схема: **Caddy** (сам получает HTTPS-сертификат) → **Next.js** → **Postgres**, всё в Docker Compose на одном сервере.
Образ собирается **у тебя на компьютере** и отправляется на сервер скриптом `scripts/deploy.sh`, поэтому серверу не нужна ни память, ни процессор на сборку, и git на нём не нужен.
Загрузки (фото/видео) и база лежат в Docker-томах и переживают обновления.

## 1. Что взять

- **VPS** в России (это требование закона для хранения персональных данных): 1 vCPU / 2 ГБ RAM / 30 ГБ NVMe хватит. ОС — **Ubuntu 24.04**. При создании вставь **публичный** SSH-ключ (`cat ~/.ssh/id_ed25519_portfolio.pub`).
- **Домен**. В DNS: `A`-запись `@` → IP сервера и `A`-запись `www` → тот же IP. Проверка: `dig +short tareev-daniil.ru`.

## 2. Настроить и защитить сервер (один раз)

С компьютера, в папке проекта (скрипт безопасно запускать повторно):

```bash
scp -i ~/.ssh/id_ed25519_portfolio scripts/server-setup.sh root@IP_СЕРВЕРА:/root/
ssh -i ~/.ssh/id_ed25519_portfolio root@IP_СЕРВЕРА 'bash /root/server-setup.sh'
```

Скрипт: обновляет систему и включает автоматические обновления безопасности, делает swap 2 ГБ, ставит Docker (с ограничением размера логов), заводит пользователя `deploy`, **запрещает вход по паролю и вход под root**, включает файрвол (открыты только SSH, 80 и 443) и fail2ban (блокирует подбор паролей SSH). Он откажется работать, если на сервере нет SSH-ключа, чтобы ты не запер себя.

**Важно:** не закрывая текущую сессию, в новом окне терминала проверь вход под новым пользователем:

```bash
ssh -i ~/.ssh/id_ed25519_portfolio deploy@IP_СЕРВЕРА
```

Дальше всё делается под `deploy`, под root больше не заходим.

## 3. Секреты на сервере

Файл с секретами живёт **только на сервере** и никогда не попадает в репозиторий.

```bash
scp -i ~/.ssh/id_ed25519_portfolio .env.prod.example deploy@IP_СЕРВЕРА:/opt/portfolio/.env.prod
ssh -i ~/.ssh/id_ed25519_portfolio -t deploy@IP_СЕРВЕРА 'chmod 600 /opt/portfolio/.env.prod && nano /opt/portfolio/.env.prod'
```

Заполни:

- `DOMAIN` — `tareev-daniil.ru` (без `https://` и без `www`).
- `POSTGRES_PASSWORD` — `openssl rand -hex 24`.
- `AUTH_SECRET` — `openssl rand -base64 32`.
- `ADMIN_EMAIL` и `ADMIN_PASSWORD_HASH`: `node -e "console.log(require('bcryptjs').hashSync('длинный-пароль', 12))"` на своём компьютере. Хеш в `.env.prod` пиши в **одинарных кавычках** и **без** экранирования `$`. Пароль админки делай длинным (от 16 символов, из менеджера паролей).
- `SITE_URL` — `https://tareev-daniil.ru`.

## 4. Первый деплой

```bash
cp .deploy.env.example .deploy.env
nano .deploy.env        # SERVER="deploy@IP_СЕРВЕРА", SSH_KEY="~/.ssh/id_ed25519_portfolio"
```

```bash
./scripts/deploy.sh
```

Скрипт сам определяет архитектуру сервера (на Mac с Apple Silicon собирает под x86 через эмуляцию, это дольше, но работает), собирает образ и отправляет его через маленький приватный реестр Docker, который работает на самом сервере и слушает только его loopback (наружу не виден; доступ только через SSH-туннель, который скрипт открывает на время отправки). Благодаря этому при следующих деплоях уходят только изменившиеся слои. Затем скрипт перезапускает контейнеры и ждёт, пока сайт ответит. Миграции базы применяются при старте. Caddy в первый раз минуту-две выпускает сертификат; потом сайт на `https://tareev-daniil.ru`, админка — `/admin/login`.

Проверить сборку без сервера: `./scripts/deploy.sh --build-only`.

## 5. Перенести контент с локальной машины (необязательно)

Чтобы забрать то, что уже введено (кейс ITECO, опыт, профиль) вместе с картинками:

```bash
# На своём компьютере, в папке проекта (локальная БД запущена):
docker exec portfolio-db-1 pg_dump -U portfolio --clean --if-exists portfolio > dump.sql
tar czf uploads.tgz -C data uploads
scp -i ~/.ssh/id_ed25519_portfolio dump.sql uploads.tgz deploy@IP_СЕРВЕРА:/opt/portfolio/
```

```bash
# На сервере (ssh deploy@IP_СЕРВЕРА), в /opt/portfolio:
cd /opt/portfolio
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d db
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T db psql -U portfolio portfolio < dump.sql
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm --no-deps --user root -v "$PWD":/src app sh -c "tar xzf /src/uploads.tgz -C /data && chown -R node:node /data/uploads"
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d
rm dump.sql uploads.tgz
```

Если не переносить, просто заполни контент заново через админку на проде.

## 6. Обновление и откат

Обновить сайт после изменений в коде: `./scripts/deploy.sh`.
Если новая версия сломалась: `./scripts/deploy.sh --rollback` (возвращает предыдущий образ; миграции базы назад не откатываются).

## 7. Бэкапы (обязательно)

Контент живёт только на этом сервере. На сервере под `deploy`:

```bash
mkdir -p ~/backups && crontab -e
```

В открывшийся файл добавь (ежедневно в 03:30, хранится 14 дней):

```
30 3 * * * cd /opt/portfolio && docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T db pg_dump -U portfolio portfolio | gzip > ~/backups/db-$(date +\%F).sql.gz && docker run --rm -v portfolio_uploads:/data:ro -v $HOME/backups:/out alpine tar czf /out/uploads-$(date +\%F).tgz -C /data . && find ~/backups -mtime +14 -delete
```

Периодически копируй `~/backups` к себе: `scp -r -i ~/.ssh/id_ed25519_portfolio deploy@IP_СЕРВЕРА:backups ~/portfolio-backups`. Бэкап на том же сервере не спасёт, если сломается сам сервер. Плюс включи автоснапшоты в панели хостера, если они есть. (Имя тома `portfolio_uploads` — это `<папка>_uploads`; проверь `docker volume ls`.)

## 8. Безопасность

**Что уже сделано**
- Вход на сервер только по SSH-ключу; пароли и вход под root отключены; fail2ban банит подбор.
- Файрвол пропускает только 22, 80, 443. Приложение (3000) и база (5432) наружу не опубликованы, они видны только внутри Docker-сети. Не добавляй `ports:` к ним в compose: Docker публикует порты в обход ufw.
- Приложение работает в контейнере под обычным пользователем `node`, без привилегий (`cap_drop: ALL`, `no-new-privileges`), не под root.
- Логин админки: после 8 неверных паролей с одного IP блокировка на 15 минут.
- Автоматические обновления безопасности ОС. Загруженные файлы раздаются с `nosniff` и CSP-песочницей (SVG не может выполнить скрипт).

**Как не получить майнер**
Майнеры в основном попадают через слабый SSH-пароль, открытый порт базы или Docker API и уязвимые зависимости. Первые два закрыты. Третье зависит от тебя:
- Обновляй зависимости, особенно **Next.js/React**: у них бывают критические уязвимости (RCE). Раз в месяц `npm outdated`, `npm audit`, потом `./scripts/deploy.sh`.
- Никогда не открывай порты 5432 и 3000 и не запускай ничего «из интернета» на сервере.
- Не используй пароль админки из других сервисов.

**Как проверить, что всё чисто** (на сервере, раз в пару недель)

```bash
sudo ss -tlnp            # слушать наружу должны только 22, 80, 443
docker ps                # ровно три контейнера: app, db, caddy
docker stats --no-stream # CPU контейнеров должен быть около нуля в простое
top -bn1 | head -15      # нет незнакомого процесса, который держит CPU
sudo fail2ban-client status sshd
last -a | head           # входы только твои
crontab -l; sudo ls /etc/cron.d   # нет незнакомых задач
```

**Если CPU постоянно 100% или появился чужой процесс:** считай сервер скомпрометированным. Чистить на месте ненадёжно. Сними снапшот для разбора, пересоздай сервер с нуля (шаги 1–4), смени `AUTH_SECRET`, пароль админки и SSH-ключ, восстанови контент из бэкапа.

## Поисковики: сайт закрыт от индексации

Пока в `/opt/portfolio/.env.prod` нет `ALLOW_INDEXING="true"`, сайт просит поисковики его **не индексировать**: `robots.txt` запрещает всё, каждый ответ (страницы, API, картинки) несёт заголовок `X-Robots-Tag: noindex`, на страницах есть `<meta name="robots" content="noindex">`. Google и Яндекс вежливо обходят такие сайты, но это просьба, а не замок: кто знает адрес, тот страницу откроет.

**Когда сайт будет готов:** впиши в `.env.prod` строку `ALLOW_INDEXING="true"` и перезапусти приложение (пересборка не нужна):

```bash
cd /opt/portfolio && docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --force-recreate app
```

После этого поисковики смогут добавить сайт (быстрее, если зарегистрировать его в Яндекс.Вебмастере и Google Search Console). Если нужна настоящая закрытость, а не просьба, скажи: можно поставить пароль на весь сайт в Caddy.

## Яндекс.Метрика

1. На https://metrika.yandex.ru → «Добавить счётчик» → укажи домен сайта. Вебвизор **не включай**.
2. Скопируй номер счётчика (только цифры).
3. На сервере впиши в `/opt/portfolio/.env.prod`: `YANDEX_METRIKA_ID="12345678"`.
4. Перезапусти: `cd /opt/portfolio && docker compose --env-file .env.prod -f docker-compose.prod.yml up -d` (пересборка не нужна).
5. Открой сайт в чистом окне: должен появиться баннер cookie. До нажатия «Принять» Метрика не грузится.
6. Упомяни Метрику и cookie в политике обработки данных (уже есть в тексте).

Пока `YANDEX_METRIKA_ID` пуст, аналитики и баннера нет.

## Мелочи

- Логин админки работает только по HTTPS (cookie с флагом `secure`), Caddy это обеспечивает.
- Размер загрузки видео ограничен только диском; Caddy лимитов не ставит.
- `www.` редиректится на основной домен.
